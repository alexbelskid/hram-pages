# Готовность Hram Pages к требованиям банка

Источник требований: `requirements_for_sites_app.pdf` (предоставленный пользователем скриншот документа банка).

## Реализовано в локальном превью

- [x] Описание церковных услуг и принцип расчёта рекомендуемого пожертвования.
- [x] Раздел «Оплата и безопасность».
- [x] Правдивое сообщение, что онлайн-оплата пока не подключена и карточные данные не собираются.
- [x] Раздел «Отмена и возврат» без выдуманной политики.
- [x] Раздел «Контакты и реквизиты» с явной пометкой о неподтверждённых юридических данных.
- [x] Рабочая форма с серверным расчётом и авторитетным ID записки.
- [x] Отдельная административная поверхность `/admin`.

## Нельзя считать выполненным без внешних подтверждений

- [ ] Собственный домен, владельцем которого является организация.
- [ ] Платный хостинг и документальное подтверждение расположения сервера в Беларуси.
- [ ] Регистрация интернет-ресурса через хостинг-провайдера в БелГИЭ, если применимо.
- [ ] Проверка необходимости реестра бытовых услуг для конкретного вида деятельности.
- [ ] Официальное наименование организации.
- [ ] УНП, дата и орган государственной регистрации.
- [ ] Юридический или почтовый адрес.
- [ ] Режим работы, официальный телефон и рабочий e-mail.
- [ ] Сведения о лицензии, если она требуется.
- [ ] Утверждённый организацией порядок отмены и возврата.
- [ ] Выбранный банк/платёжный провайдер и подписанный договор.
- [ ] Подтверждённые API/webhook-контракты, тарифы и правила minor units.
- [ ] Официальный пакет логотипов провайдера и платёжных систем.
- [ ] Реальный provider-backed refund flow.
- [ ] Production-аутентификация администраторов, роли, MFA и отзыв сессий.
- [ ] PostgreSQL, backup/restore drill, мониторинг и правила хранения/удаления персональных данных.

## Не применяется к сайту услуг по сноске документа

- Регистрация интернет-магазина в Торговом реестре.
- Дата изготовления и гарантийный срок товара.

Эти исключения нужно окончательно подтвердить у банка применительно к юридической модели храма и формату платежа/пожертвования.

## Release gate

Публичный deploy — отдельное действие уровня `R3`. Он выполняется только после:

1. согласования фронта Сергеем;
2. успешных тестов и независимых review;
3. подготовки точного release-артефакта и SHA-256;
4. отдельного явного одобрения именно этого SHA-256;
5. deploy через идемпотентный release key;
6. read-back публичной формы, API, `/admin` и состояния сервиса.
